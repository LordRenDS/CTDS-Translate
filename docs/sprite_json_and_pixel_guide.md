# Руководство по структуре JSON-разметки спрайтов и расчету пикселей в графических редакторах

Данный документ описывает формат JSON-файлов разметки спрайтовых атласов Nintendo DS (на примере `obj_logo_new.json`), архитектуру аппаратных тайлов и OAM, а также правила безошибочного переноса координат в графические редакторы (Aseprite, Photoshop и др.).

---

## 1. Структура JSON-файла разметки (NCER / NCGR)

В Chrono Trigger DS и играх на Nintendo DS сложные экранные надписи и меню компонуются в виде **атласа ячеек** (`is_cell_sheet: true`). 
JSON-файл связывает плоский рисунок PNG с бинарными ресурсами ROM:
- **NCGR (Nitro Character Graphics Resource)** — линейный массив пиксельных тайлов 8×8.
- **NCER (Nitro Cell Resource)** — банк ячеек (Cell), определяющий, из каких аппаратных блоков (OAM) и тайлов собирается каждая экранная надпись.
- **NCLR (Nitro Color Resource)** — цветовая палитра.

### 1.1. Глобальные поля заголовка

```json
{
  "format": "NCGR",
  "is_cell_sheet": true,
  "is_8bpp": false,
  "num_tiles": 316,
  "sheet_width": 256,
  "sheet_height": 250,
  "compression_layers": 1,
  "ncgr_path": "extracted rom\\data\\title\\obj\\obj_logo_new.NCGR",
  "ncer_path": "extracted rom\\data\\title\\obj\\obj_logo_new.NCER",
  "nclr_path": "extracted rom\\data\\title\\obj\\obj_logo_new.NCLR",
  "base_palette_index": 0,
  "components": [ ... ]
}
```

| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `format` | string | Формат графики (для спрайтов всегда `"NCGR"`). |
| `is_cell_sheet` | boolean | `true` — изображение является атласом ячеек NCER (а не сплошным фоновым тайлмапом). |
| `is_8bpp` | boolean | `false` — 4 бита на пиксель (16 цветов на субпалитру). `true` — 8 бит (256 цветов). |
| `num_tiles` | integer | Общее число тайлов 8×8 в файле NCGR (для `obj_logo_new` это 316, от 0 до 315). |
| `sheet_width`, `sheet_height` | integer | Габариты общего PNG-изображения в пикселях. |
| `compression_layers` | integer | Количество слоев сжатия LZ10 (в CTDS обычно `1`). |
| `components` | array | Список всех экранных надписей (ячеек Cell), расположенных на холсте. |

---

### 1.2. Секция ячейки (`components`)

Каждый элемент массива `components` описывает одну логическую надпись на экране (например, надпись «Режим Игры»):

```json
{
  "type": "cell",
  "cell_idx": 0,
  "min_x": 0,
  "min_y": 0,
  "width": 96,
  "height": 24,
  "canvas_x": 8,
  "canvas_y": 8,
  "oams": [ ... ]
}
```

| Поле | Описание |
| :--- | :--- |
| `type` | `"cell"` для игровой надписи или `"uncovered"` для неиспользуемых тайлов. |
| `cell_idx` | Порядковый номер ячейки в банке NCER (например, 0 = "Режим Игры", 1 = "Режим Боя"). |
| `canvas_x`, `canvas_y` | **Координаты левого верхнего угла ячейки на общем PNG-холсте.** |
| `width`, `height` | Полные габаритные размеры надписи (ширина и высота ограничивающего прямоугольника). |
| `min_x`, `min_y` | Внутреннее минимальное смещение среди всех OAM ячейки (обычно 0, но в ячейках со сдвигом может быть отрицательным, например `-2`). |
| `oams` | Список физических блоков OAM, из которых составляется надпись. |

---

### 1.3. Секция аппаратного блока (`oams`)

Железо Nintendo DS не умеет выводить спрайты произвольного размера — оно складывает их из стандартных блоков OAM (Object Attribute Memory).

```json
{
  "x": 0,
  "y": 0,
  "w": 32,
  "h": 16,
  "tile": 20,
  "pal": 0,
  "rot": 0,
  "hflip": 0,
  "vflip": 0
}
```

| Поле | Описание |
| :--- | :--- |
| `x`, `y` | Позиция этого кусочка относительно левого верхнего угла надписи. |
| `w`, `h` | Ширина и высота кусочка в пикселях. Должны строго соответствовать аппаратным размерам NDS! |
| `tile` | **Номер начального тайла 8×8 в NCGR**, с которого этот блок берет графику. |
| `pal` | Индекс субпалитры (0..15). |
| `rot` | Режим аффинных трансформаций (вращение/масштабирование): 0 — выключен, 1 — включен. |
| `hflip`, `vflip` | Отражение по горизонтали/вертикали (1 — отразить, 0 — нет). |

## 2. Что такое тайл в Nintendo DS?

**Тайл (Tile)** — это базовый, неделимый строительный блок 2D-графики размером **ровно 8×8 пикселей**.

В видеопамяти NDS пиксели не лежат единой сплошной строкой. Вместо этого изображение «нарезано» на тысячи таких плиток 8×8. В файле `obj_logo_new.NCGR` все 316 тайлов лежат друг за другом в виде плоского одномерного массива:

$$\text{[Тайл 0]} \quad \text{[Тайл 1]} \quad \text{[Тайл 2]} \quad \dots \quad \text{[Тайл 315]}$$

- **Размер одного тайла в байтах:**
  - При 4bpp (16 цветов): 8 × 8 пикселей × 4 бита = 256 бит = **32 байта**.
  - При 8bpp (256 цветов): 8 × 8 пикселей × 8 бит = 512 бит = **64 байта**.

### 2.1. Как OAM использует тайлы

Поле `"tile": N` в объекте OAM указывает **начальный номер тайла** в этом массиве. 

Количество тайлов, которое «съедает» один OAM, равно площади блока, деленной на 64 (площадь одного тайла 8×8):

$$\text{Количество тайлов} = \frac{W \times H}{64}$$

Например, для блока `w: 32, h: 16`:
$$\text{Количество тайлов} = \frac{32 \times 16}{64} = 8 \text{ тайлов}$$

Если этот блок начинается с `"tile": 0`, он использует тайлы **с 0 по 7**:
```text
           ◄────────────── 32 пикселя ─────────────►
       8 px      8 px      8 px      8 px
    ┌─────────┬─────────┬─────────┬─────────┐ ▲
8 px│ Тайл 0  │ Тайл 1  │ Тайл 2  │ Тайл 3  │ │
    ├─────────┼─────────┼─────────┼─────────┤ 16 пикселей
8 px│ Тайл 4  │ Тайл 5  │ Тайл 6  │ Тайл 7  │ │
    └─────────┴─────────┴─────────┴─────────┘ ▼
```

Следующий блок в цепочке должен начинаться с тайла:
$$\text{tile}_{\text{следующий}} = 0 + 8 = \mathbf{8}$$

### 2.2. Стандартные аппаратные размеры OAM на Nintendo DS

Каждый OAM обязан иметь один из следующих размеров:

| Форма | Размеры ($W \times H$, пикс.) | Число тайлов 8×8 | Сетка тайлов |
| :--- | :--- | :--- | :--- |
| **Квадрат** | **8×8** | 1 | 1×1 |
| | **16×16** | 4 | 2×2 |
| | **32×32** | 16 | 4×4 |
| | **64×64** | 64 | 8×8 |
| **Широкий** | **16×8** | 2 | 2×1 |
| | **32×8** | 4 | 4×1 |
| | **32×16** | 8 | 4×2 |
| | **64×32** | 32 | 8×4 |
| **Высокий** | **8×16** | 2 | 1×2 |
| | **8×32** | 4 | 1×4 |
| | **16×32** | 8 | 2×4 |
| | **32×64** | 32 | 4×8 |

## 3. Памятка по расчету пикселей в графических редакторах

При переносе координат из JSON в редакторы (Aseprite, Photoshop, GIMP, Paint.NET) легко ошибиться на 1 пиксель из-за дискретности растровой сетки.

### 3.1. Точка старта всегда берется 1-в-1 из JSON

> **Главное правило:** Если в JSON написано `canvas_x: 8, canvas_y: 8`, курсор в редакторе ставится **СТРОГО в точку (8, 8)**. Никаких «7» или «9»!

### 3.2. Почему «Начало + Размер» дает ошибку на 1 пиксель?

Если прямоугольник начинается в точке **8** и имеет размер **24 пикселя**, математическое сложение дает:
$$8 + 24 = 32$$

Если провести линию или рамку от координаты `8` до координаты `32`:
- Точка 8 — это **1-й пиксель**
- Точка 9 — это **2-й пиксель**
- ...
- Точка 31 — это **24-й пиксель**
- Точка 32 — это уже **25-й пиксель!** (лишний пиксель!)

Потому что начальная точка `8` — **уже входит** в размер!

---

### 3.3. Формула конечной координаты

Чтобы получить границу последнего пикселя в редакторе, всегда вычитайте единицу:

$$\mathbf{Конечная\ координата} = \mathbf{Начало} + \mathbf{Размер} - \mathbf{1}$$

#### Примеры:
- **Размер 24 пикселя**, старт в **8**:
  - Начало: `8`
  - Конец: $8 + 24 - 1 = \mathbf{31}$
  - *(Координаты с 8 по 31 включительно = ровно 24 пикселя).*

- **Размер 48 пикселей**, старт в **0**:
  - Начало: `0`
  - Конец: $0 + 48 - 1 = \mathbf{47}$
  - *(Координаты с 0 по 47 включительно = ровно 48 пикселей).*

- **Размер 64 пикселя**, старт в **64**:
  - Начало: `64`
  - Конец: $64 + 64 - 1 = \mathbf{127}$
  - *(Координаты с 64 по 127 включительно = ровно 64 пикселя).*

---

### 3.4. Пересчет координат конкретного OAM на общий PNG-холст

Чтобы найти, где именно на большой картинке PNG лежит нужный кусочек OAM:

$$\text{X}_{\text{start}} = \text{canvas\_x} + (x - \text{min\_x})$$
$$\text{X}_{\text{end}} = \text{X}_{\text{start}} + w - 1$$

$$\text{Y}_{\text{start}} = \text{canvas\_y} + (y - \text{min\_y})$$
$$\text{Y}_{\text{end}} = \text{Y}_{\text{start}} + h - 1$$

#### Пример: Правое слово «Игры» в Cell 0
- `canvas_x: 8`, `canvas_y: 8`, `min_x: 0`, `min_y: 0`
- OAM 0: `x: 48, y: 0, w: 32, h: 16`
- **X на PNG:** от $8 + 48 = \mathbf{56}$ до $56 + 32 - 1 = \mathbf{87}$
- **Y на PNG:** от $8 + 0 = \mathbf{8}$ до $8 + 16 - 1 = \mathbf{23}$

### Памятка про шрифты

Если использовать режим разметки, то самая левая и самая нижняя граница включаются в ячейку, а уже последующие за ними рамки отмечают конец ячейки, и следующая начинается за этой рамкой.
Пример с горизонтальной границей:
| <-(граница рамки входит в ячейку)-> | <-(не входит в ячейку)  (входит в ячейку)-> |
С вертикальной аналогично, но с низу.

## 4. Практические приемы для редакторов

1. **Используйте инструмент «Прямоугольное выделение» (Marquee Tool)**:
   - Поставьте курсор на начальную координату (`X: 8, Y: 8`).
   - Нажмите левую кнопку мыши и тяните выделение.
   - Следите за инфо-панелью редактора (окно `Info` / строка состояния): тяните, пока там не появится требуемый размер `W: 96, H: 24` (или `32x16`). Редактор автоматически выделит диапазон пикселей правильно.

2. **Включите сетку 8×8 пикселей (Grid)**:
   - В Aseprite: `View -> Grid -> Grid Settings -> Width: 8, Height: 8`.
   - Включите `Snap to Grid` (Привязка к сетке).
   - Так как все OAM кратны 8, выделения и направляющие будут автоматически примагничиваться к границам тайлов.

3. **Используйте готовый шаблон разметки**:
   - В проекте сгенерирован размеченный файл:
     [`translated image/title/obj/obj_logo_new_layout_guide.png`](../translated%20image/title/obj/obj_logo_new_layout_guide.png)
   - Уменьшите его масштаб в 4 раза (до 256×250) и вставьте в редактор отдельным полупрозрачным слоем сверху — границы всех ячеек, швов и зазоров будут видны прямо во время рисования.
